# MathBlitz — What Every File Is (Plain-English Guide)

This document explains **every file and folder** currently in the project, in plain language. It's grouped by "why it's here" rather than alphabetically, because most of the files (everything under `android/`, `ios/`, `web/`, `.dart_tool/`, `build/`) were auto-generated by tools and you'll never hand-edit them — only a handful of files are ones we actually wrote by hand, and those are the ones that matter for understanding the app.

**Legend:**
- 🟢 = we wrote this by hand, this is real project content
- ⚙️ = auto-generated machinery, don't hand-edit, safe to regenerate
- 📝 = config/instructions file, occasionally worth reading or tweaking

---

## 1. The files that actually matter (🟢 hand-written)

These live in `lib/` (the app's real code) and `test/` (the automated checks for that code). Everything else in this document is scaffolding around these.

### `lib/main.dart` 🟢
The **entry point** — the very first thing that runs when the app launches. Right now it's a deliberately blank placeholder: it just shows a screen that says "MathBlitz — under construction." No real game screens exist yet on purpose (the build plan forbids touching real UI until the logic underneath is tested and solid).

### `lib/models/puzzle.dart` 🟢
The **blueprint for one quiz question**. Defines what fields every question has: an ID, a category (math test vs. reasoning test), a specific type (e.g. arithmetic, true/false, family-tree relationship, shape identification), the question text, up to 4 answer options, which one is correct, a difficulty level (1–4), and a time limit. This file can't *generate* a question — it only describes the shape one must take. Also includes the code that converts a `Puzzle` to/from the text format (JSON) used for saving.

### `lib/models/game_session.dart` 🟢
The **blueprint for one round of play**: when you started, your current score, combo streak, lives remaining, the full list of questions you were asked, and a matching list of whether you got each one right. Also tracks whether this was a "Daily Challenge" and, if so, which random-number seed generated it (so the same daily puzzle can be reproduced for everyone).

### `lib/models/player_stats.dart` 🟢
The **blueprint for your saved profile** — the stuff that persists across app restarts: high score, current day-streak, last-played date, total coins, and your best score at each difficulty tier.

### `test/models/puzzle_test.dart` 🟢
Automated checks for `puzzle.dart`. The main check: convert a `Puzzle` to text and back, and confirm you get back exactly what you started with — including tricky details like whether the correct answer was a number, a true/false, or a word. Also checks things like "an unrecognized question type should throw an error, not silently misbehave." 13 checks total.

### `test/models/game_session_test.dart` 🟢
Same idea for `game_session.dart` — 6 checks, including that a session containing a list of real questions round-trips correctly.

### `test/models/player_stats_test.dart` 🟢
Same idea for `player_stats.dart` — 5 checks, including that a table of "best score per difficulty" round-trips its number keys correctly (a subtle JSON gotcha: JSON only allows text keys, so `1` has to become `"1"` and back).

**Running `flutter test` runs all of the above automatically — currently 24 checks, all passing.**

## 3. Root-level project files

### `ARCHITECTURE.md` 📝
The **master build plan** for the entire app — every phase, every file, every test that has to pass before moving on. This is the document I follow step-by-step; it's why work happens in small, gated chunks instead of all at once.

### `pubspec.yaml` 📝
Flutter's "shopping list & ID card" for the project: the project's name (`math_blitz`), and the list of external code libraries it depends on. Right now that list has exactly one thing: `uuid`, a tiny library that generates unique random ID codes (used for `Puzzle.id`).

### `pubspec.lock` ⚙️
The **exact version numbers** of every library from `pubspec.yaml` (and everything *those* libraries depend on), locked down so the project builds identically on any machine, today or a year from now. Auto-updated whenever you add/change a dependency — never hand-edited.

### `analysis_options.yaml` 📝
Turns on Dart's built-in **code style checker** (`flutter analyze`), which flags sloppy or risky patterns as the code is written — before they become bugs.

### `.gitignore` 📝
Tells Git (the save-history tool) **what not to bother saving** — temporary files, build caches, IDE settings — because they're either regenerated automatically or are personal-machine-only clutter. We just added a line here so this very `Documents/` folder never gets pushed to GitHub, per your "local only" request.

### `.metadata` ⚙️
Flutter's own internal bookkeeping — records which exact Flutter version created this project, so Flutter's tools can detect version mismatches later. You'll never edit this by hand.

### `README.md` 📝
The generic placeholder description Flutter's project generator writes by default. Worth rewriting later with your own description of what MathBlitz is — currently still says "A new Flutter project."

### `.mcp.json` 📝
A small config file connecting **me (Claude)** to a free tool called Context7, which feeds me live, accurate Flutter/Dart documentation while I'm writing code, so I'm less likely to use outdated or made-up commands. Doesn't affect your app at all — it's a tool for how I work on it.

### `Maths_Test.code-workspace` 📝
A VS Code "workspace" file — remembers editor window/folder setup for this project in VS Code. Yours from before this project started; untouched by us.

### `math_blitz.iml`, `.idea/` ⚙️
Config files for JetBrains IDEs (Android Studio / IntelliJ) — remembers project structure/settings *if* you ever open this project in one of those editors instead of VS Code. Harmless if you never use them; auto-regenerated if deleted.

## 4. Platform packaging folders (⚙️ auto-generated, basically never hand-edited)

Flutter's whole pitch is "write the app once, package it for multiple platforms." These three folders are that packaging machinery — they contain almost no game logic, just the scaffolding each platform's app store requires.

### `android/` — packaging for Android phones
- `android/app/build.gradle.kts`, `android/build.gradle.kts`, `android/settings.gradle.kts` — Android's build-system config files (Gradle is Android's equivalent of a recipe that turns code into an installable `.apk`/`.aab` file).
- `android/app/src/main/kotlin/com/mathblitz/math_blitz/MainActivity.kt` — the one-line Android entry point that just hands control over to Flutter.
- `android/app/src/main/java/io/flutter/plugins/GeneratedPluginRegistrant.java` — auto-generated glue code that registers any Android-specific plugins the app uses (none yet).
- `android/app/src/main/AndroidManifest.xml` (+ `debug`/`profile` variants) — Android's required "ID card" for an app: its name, permissions, icon, entry point.
- `android/app/src/main/res/mipmap-*/ic_launcher.png` — the app icon at 5 different pixel resolutions, one per phone screen density (mdpi/hdpi/xhdpi/xxhdpi/xxxhdpi) — Android needs each size pre-rendered rather than scaling one image.
- `android/app/src/main/res/drawable*/launch_background.xml`, `values*/styles.xml` — the plain background/theme shown for a split second while the app is loading.
- `android/gradle/wrapper/gradle-wrapper.jar` + `.properties`, `android/gradlew`, `android/gradlew.bat` — a self-contained copy of the Gradle build tool so the project builds with the exact right version without you installing Gradle separately.
- `android/gradle.properties`, `android/local.properties` — build settings and machine-specific paths (e.g. where the Android SDK lives on *this* computer — not portable, regenerated per machine).
- `android/.gitignore` — Android-specific extra ignore rules, layered on top of the root `.gitignore`.

### `ios/` — packaging for iPhones/iPads
- `ios/Runner.xcodeproj/`, `ios/Runner.xcworkspace/` — the Xcode project files (Xcode is Apple's equivalent of Android Studio) — you'd only open these on a Mac.
- `ios/Runner/AppDelegate.swift`, `SceneDelegate.swift` — the iOS equivalent of `MainActivity.kt`: minimal glue code handing control to Flutter.
- `ios/Runner/Info.plist` — iOS's required "ID card" for the app (name, version, permissions).
- `ios/Runner/Assets.xcassets/AppIcon.appiconset/*.png` — the app icon at *many* required sizes (iOS is stricter than Android about exact pixel dimensions for each context: home screen, settings, spotlight search, etc. — that's why there are 13 separate icon files).
- `ios/Runner/Assets.xcassets/LaunchImage.imageset/` — the loading-screen image, 3 resolutions.
- `ios/Runner/Base.lproj/LaunchScreen.storyboard`, `Main.storyboard` — visual layout files for the loading screen and (unused, Flutter-managed) main screen.
- `ios/Runner/GeneratedPluginRegistrant.h`/`.m`, `ios/Flutter/ephemeral/...` — auto-generated/rebuilt-on-demand glue and package-manager scratch files; genuinely disposable.
- `ios/Flutter/*.xcconfig`, `Generated.xcconfig`, `flutter_export_environment.sh` — build settings Flutter injects so Xcode knows how to compile the Flutter half of the app.
- `ios/RunnerTests/RunnerTests.swift` — an empty placeholder for native-iOS-level tests (different from our Dart tests in `test/`), unused so far.
- `ios/.gitignore` — iOS-specific extra ignore rules.

### `web/` — packaging for running in a browser
- `web/index.html` — the actual HTML page a browser loads to start the app.
- `web/manifest.json` — metadata that lets a browser treat the web app like an installable app ("Add to Home Screen").
- `web/favicon.png`, `web/icons/Icon-*.png` — the browser-tab icon and home-screen icons at a few sizes.

## 5. Auto-generated caches (⚙️ safe to delete, git-ignored, not saved to GitHub)

These reappear automatically the moment you run any `flutter` command — they're working scratch space, not source material.

- **`.dart_tool/`** — Dart/Flutter's internal cache: which package versions are actually resolved, code-generation bookkeeping, editor-integration hints.
- **`build/`** — output from the last time tests/builds ran: compiled test bundles, font files copied in for the test run, shader files, etc.

If either folder vanished entirely, the next `flutter test` or `flutter run` would simply recreate whatever it needs.
